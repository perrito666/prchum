# Working on prchum

This file is for anyone sending changes — people and coding agents
alike. It is not a style guide about braces; it records the handful of
decisions the codebase is built on, so a change lands with the grain
instead of across it.

## The shape of the project

A portable Rust core behind a C ABI, and a thin macOS shell on top:

- `core/prchum-core` — diffs, comments, anchoring, sources, forges,
  syntax, config. No UI, no platform assumptions.
- `core/prchum-forge` — the forge adapters.
- `core/prchum-ffi` — the C entry points, built as `libprchum.a`.
- `macos/Sources/CPrchum/include/prchum.h` — generated by cbindgen and
  **committed**. Regenerate it in the same commit as the FFI change.
- `macos/Sources/PrchumKit` — Swift wrappers over the C API.
- `macos/Sources/Prchum` — AppKit: windows, menus, rendering.

The dividing line is the one that matters: **logic belongs in the
core**. If a rule can be expressed without a window, it goes in Rust,
where it can be tested. The shell arranges views, translates events, and
otherwise stays boring. A second platform should be able to sit on the
same core without moving anything.

## FFI conventions

Every entry point follows the same shape, and a new one that does not
will be asked to:

- Opaque handles; no Rust types cross the boundary.
- Strings in as `(pointer, length)` UTF-8; strings out nul-terminated
  and released with `pc_string_free`.
- Structured results travel as JSON strings rather than C structs.
- Every entry point wraps its body in `catch_unwind`. A panic must never
  unwind into Swift.
- The session is internally synchronized; call it from any thread.

## The rules that carry weight

**Rendered rows are never a comment's location.** What the reviewer sees
is a rendering, and renderings change — a comment box appears, a hunk
folds, the branch moves. A comment anchors to a semantic location:
path, side, line range, and a short context anchor with a hash of the
line's content. When code needs "where the caret is", it asks for the
semantic location, not an offset into the text view.

**Relocation is conservative.** On reopening, a draft matches exactly,
or matches a single unambiguous move, or becomes orphaned. Orphaned
drafts are kept and shown, and never submitted. Guessing is worse than
saying "this moved and I am not sure where".

**Submission is retry-safe.** Comments the forge accepts are removed
from local drafts as they land, so a partial failure can be retried
without posting anything twice.

**Prchum never handles your credentials.** Forge access shells out to
the CLI you already use — `gh`, `glab`, `fj` — and reads no tokens of
its own. A new forge is a command template, not a stored secret.

**Use what exists; manage only what you made.** The worktree rule: if
the branch is already checked out somewhere, use that checkout and leave
it alone. Only worktrees prchum created are recorded in the registry,
and only those are ever removed.

**Config stays hand-editable.** `config.json` is a file a person edits.
Unknown keys survive every save, a file that fails to parse is never
overwritten, and a bad value produces a warning rather than a reset.

**Every operation is a named action.** Actions live in the `ActionID`
registry, each with a menu item and a default key equivalent that the
`keys` map can rebind. Nothing is mouse-only, and nothing is
keyboard-only. There is no modal editing grammar here — the model is a
menu with good keys, not vim.

## Comments in code

Write the comment the next reader needs: the constraint, the reason, the
thing the code cannot say about itself. Not what the next line does, not
how the change came about, not a note to the reviewer.

Skip the qualifiers — "honestly", "actually", "obviously", "simply".
They add nothing and read as filler.

## Tests

- `make test` — the core's unit tests. Anything with logic in it gets
  one here.
- `make smoke` — a headless suite that drives real sessions end to end
  through the shell's own code paths. A feature that touches the shell
  gets a scenario.

Both should pass before a pull request.

## Commits and pull requests

Commit in logical steps: one coherent change per commit, with a message
that says what it does and, where it is not obvious, why. A branch of
five readable commits is better than one enormous one.

Do not add AI co-author or "generated by" trailers to commits. Author
your work under your own name.

Do not cut releases. Tags are the maintainer's call.

## Documentation

The site under `docs/` is trilingual, using suffixes: `page.md`,
`page.es.md`, `page.fr.md`. A change to one is a change to all three —
a page that exists only in English is a page that will drift. Build with
`mkdocs build --strict` before sending it.
