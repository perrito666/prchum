# Prchum — Planning Document

A native macOS code-review client: leanreview's functionality rebuilt on
textchum's architecture. It reviews a **patch/diff file**, a **local git
comparison**, a **GitHub pull request**, or a **GitLab merge request** in the
same app: navigate the diff, attach draft comments anchored to semantic diff
locations, then **export them as Markdown / review-exchange JSON** or
**submit them as a real review**.

Like leanreview, it is a review client, not a git client: the installed
`git`, `gh`, and `glab` handle repository and forge semantics; prchum owns
navigation, rendering, review state, and comments.

## 1. Product goals

**In scope**
- Fast native macOS app (AppKit/SwiftUI): a diff viewer with unified and
  side-by-side layouts, syntax highlighting, folding, search, and a
  changed-files sidebar.
- Draft comments anchored to semantic locations (path, side, line range,
  surrounding context) that survive layout changes and head-commit moves.
- The full leanreview source matrix: patch file, local git range, GitHub PR,
  GitLab MR, and the review-exchange (`*.review.json`) format for the
  offline LLM review loop.
- Real review submission through `gh`/`glab` — their auth, their enterprise
  hosts, one atomic review on GitHub, mapped submission on GitLab.
- Markdown export of notes, and exchange-file writeback on every save.

**Out of scope (deliberately)**
- Editing code. Prchum reviews changes; it never modifies the tree.
- Being a git GUI: no staging, branching, merging, or history browsing.
- Its own forge credentials: `gh`/`glab` own tokens and hosts, always.
- Cross-platform UI at first. The core stays portable (the textchum/Ghostty
  model keeps the door open); only macOS is planned in these phases.

## 2. Architecture: compiled core + native shell (the textchum model)

Identical split to textchum: a portable Rust core behind a fully native
Swift shell, meeting at a C ABI.

```
┌──────────────────────────────────────────────┐
│ macOS app (Swift, AppKit + SwiftUI)          │
│  windows, diff rendering, input, sidebar,    │
│  comment editor, submit sheet, settings      │
└───────────────▲──────────────┬───────────────┘
                │ C ABI        │ callbacks (events)
┌───────────────┴──────────────▼───────────────┐
│ libprchum (compiled core, one static lib)    │
│  diff model + parser · locations/anchors     │
│  review session: drafts, threads, relocation │
│  sources: patch/git/PR/MR/exchange           │
│  forge seam (gh/glab subprocesses)           │
│  export (markdown/exchange) · config         │
└──────────────────────────────────────────────┘
```

**Division of labor rule of thumb:** anything that answers "what changed,
and what do we know about it?" lives in the core. Anything that answers
"how does it look and feel on macOS?" lives in the shell. The core never
draws; the shell never parses a diff or talks to a forge.

The load-bearing design rule carries over from leanreview verbatim:
**rendered rows are never canonical comment locations.** Comments anchor to
a semantic `Location` (path, side, 1-based line range, context anchor with
a content hash) owned by the core. Unified/split, folding, and wrapping are
shell-side *projections*; the shell asks the core "what location is this
row?" and "place this comment at this location", never the reverse.

Where textchum's core owns a mutable rope, prchum's core owns an
**immutable review session**: the parsed diff plus mutable review state
(drafts, staged replies, summary, event). That makes the FFI simpler than
textchum's — there is no per-keystroke sync protocol; the expensive flows
(fetch PR, fetch file content, submit) are async events.

### The FFI boundary (textchum's six conventions, unchanged)

- One C header (`prchum.h`), generated by cbindgen, committed so Swift
  tooling works without a Rust toolchain; CI checks drift.
- **Handle-based API**: opaque `PcApp`, `PcSession`. `Box::into_raw`/
  `from_raw`, paired `pc_*_free`.
- Strings in as UTF-8 `(pointer, length)`; strings out nul-terminated,
  freed with `pc_string_free`. Fallible calls return `bool`; `false` means
  inputs were validated, rejected, and nothing changed. Panics never cross
  (`catch_unwind` everywhere).
- **Calls in** are synchronous and cheap (row queries, add/edit/delete
  draft, fold state is shell-side). **Events out** (PR fetched, threads
  arrived, file content ready, submit finished, image fetched) go through a
  single registered callback with a tagged `PcEvent` on one core-owned
  dispatch thread; the Swift side hops to the main actor.
- Data shapes by cost, textchum's mixed policy: `#[repr(C)]` structs for
  bulk hot data (diff lines for a file, span tables), JSON strings for
  structured occasional payloads (PR metadata, threads, comment lists,
  submit results), delimited strings for flat lists (file names).
- Threading contract: shell calls in from the main thread only; the core
  owns worker threads (forge subprocesses, file fetches) and dispatches
  events from exactly one thread.

### Diff rendering strategy

No text editing means no TextKit sync problem — the riskiest part of
textchum does not exist here. The diff view is a read-only,
line-oriented custom `NSView` (rows drawn with Core Text / `NSAttributedString`
line fragments): one visual row per drawn line, gutters for old/new line
numbers and comment markers (`●` drafts, `◆` threads), inline comment
boxes as interleaved rows. This is closer to a table than an editor;
`NSTableView`-style row reuse over core-provided row models is the plan,
with a plain flat draw as the fallback if row reuse fights the inline
boxes. Selection is by diff line (GitHub semantics: one continuous range
on one side), not by character.

Comment *editing* uses a plain `NSTextView` in an inline box (GitHub-style),
not `$EDITOR` — a native app has no reason to shell out for text entry.

### Syntax highlighting

tree-sitter in the core, reusing textchum's approach (grammar crates,
styled spans, the same theme table shape). leanreview's three-tier fidelity
(whole-file pass per side when content is available, else per-hunk, else
per-line) ports as core logic; the shell just gets `(start, end, style)`
spans per line. Chroma is Go-only; tree-sitter is the native equivalent
and textchum already proves the integration. Start with the same ~16
grammar set.

### Forge integration

Kept exactly as leanreview does it: **shell out to `gh api` / `glab api`**
from the core (subprocesses are portable Rust; `std::process` + the same
argument shapes). Auth, token storage, and enterprise hosts remain the
CLI's already-solved problem. The `Forge` trait mirrors leanreview's
interface: pull request metadata, canonical diff, threads, create review,
general comments, replies, file content, attachments. GitHub submits one
atomic review; GitLab maps to positioned discussions + note + approve,
with the ranged-suggestion rewrite. One subtlety to carry over: apps
launched from Finder inherit a minimal PATH — adopt the login shell's PATH
before spawning anything (textchum's `adoptLoginShellPath()` exists for
exactly this).

## 3. Subsystem designs

### 3.1 Diff model (core)

Direct port of leanreview's model: `Side` (LEFT/RIGHT), `LineKind`
(context/addition/deletion/metadata), `FileStatus` (M/A/D/R/C/binary),
`DiffLine { kind, text, raw, old_line, new_line, patch_position }`,
`Hunk`, `FileDiff { old_path, new_path, status, hunks, raw_patch }`.
Rules that carry over verbatim:

- Tab expansion at parse time for display; `raw` keeps the verbatim form,
  and **anything leaving the program as code uses raw** (suggestion
  fences, patches).
- GitHub-style patch positions computed at parse (an `@@` header consumes
  a position).
- Parser is hand-rolled unified-diff (git headers, renames, binary,
  `\ No newline`); property: parse(render(x)) == x on git output.

### 3.2 Locations, anchors, relocation (core)

`Location { path, commit_oid, side, start_line, end_line, anchor }` with
`ContextAnchor { hunk_header, before[≤3], anchor_text, after[≤3],
content_hash }`. Relocation is leanreview's conservative algorithm: exact
context match at the recorded line → Exact; unique anchor-text match
elsewhere (following renames) → Moved; ambiguous or absent → **Orphaned,
never guessed, never dropped, never submitted**. Runs when a PR head moves
between sessions.

### 3.3 Review session (core)

One `Session` per source: parsed files + `DraftReview { source_key, title,
head_oid, comments, general, summary, event }`. Draft comments carry
`local_id`, location, body, optional `reply_to` (host thread id), snippet,
state (`active | stale | orphaned | dismissed`), author/at/replies (for the
exchange conversation). Dismissed ≠ deleted — the verdict is information
for the other side of a conversation. Persistence: one JSON file per
source key under `~/Library/Application Support/Prchum/drafts/`, atomic
writes, same stable source-key scheme as leanreview (`patch-<hash>`,
`git-<root>-<spec>`, `gh-<host>-<owner>-<repo>-prN`, `exchange-<hash>`).

### 3.4 Sources (core)

The leanreview matrix: patch file, local git (`working tree`, `--staged`
equivalent, base ref, explicit range — driven by the `git` binary),
GitHub PR / GitLab MR via the forge seam (canonical diff from the host so
positions always match), and the **review-exchange format** (version 1,
`leanreview_review` sniff key, patch-as-line-array, byte-identical round
trips, writeback on every save) — full compatibility with leanreview's
format so the two clients interoperate on the same files. Full-file
context content per side (for context view and whole-file highlighting)
comes through the same seam with a content-addressed disk cache
(`~/Library/Caches/Prchum/`, 14-day/50 MiB cleanup).

### 3.5 Shell (Swift app)

- AppKit backbone, one review window per source; SwiftUI for chrome
  (sidebar, settings, submit sheet), same split as textchum.
- **Main window**: changed-files sidebar (status glyph, path, `●N` draft
  badge) as an `NSSplitViewItem`, diff view center, toolbar with layout
  toggle (unified/split), context toggle, syntax mode, and submit.
- **Keyboard-first**: leanreview's grammar is the spec — j/k/J/K, ]c/[c,
  ]f/[f, gg/G, counts, v/V selection, c comment, e edit, dd delete,
  x dismiss, za/zR/zM folds, / search, t layout, T context, i previews,
  s submit — implemented as key equivalents over the diff view, with
  every action also in the menu bar (discoverable, rebindable later).
- **Comments**: inline boxes under their anchor line (drafts `●`, host
  threads `◆`, replies indented, `[state]` tags), native Markdown
  rendering with real images (`AttributedString`; attachments fetched by
  the core through the forge with the signed-URL resolution leanreview
  does). Inline editor: text view + Comment/Cancel, ⌘↩ to save.
- **Review navigator**: a drawer/overlay listing all drafts and host
  threads (leanreview's `C`), click to jump.
- **PR info** (`p`): title, author, base←head, description, conversation
  comments; **general comments** screen with staged drafts.
- **Submit sheet** (`s`): counts, summary editor, event picker
  (Comment/Approve/Request changes), orphan warning; nothing sent before
  confirmation; retry-safe partial-failure handling (the core records
  what the host accepted even on error — a retry never double-posts).
- **Open flow**: drag a `.diff`/`.patch`/`.review.json` onto the app,
  File → Open, an "open PR by URL/number" field, and a discovery list
  (leanreview `--list`: `gh search prs` / glab equivalent with named
  filters) shown when launched without a target.
- A `prchum://` URL scheme + tiny `pr` CLI script later, mirroring `chum`.

### 3.6 Configuration

textchum's rules, leanreview's content: JSON at
`~/Library/Application Support/Prchum/config.json`, GUI-managed and
hand-editable — broken files never clobbered (`.bak` + warning), unknown
keys survive, atomic writes. Settings: appearance (system/light/dark),
theme, syntax mode, tab width, context lines, wrap, author, images on/off,
list engine/filters, keymap overrides. Read by the core; the Settings
window writes through.

### 3.7 Appearance & themes

Same design as textchum §3.7: appearance mode in config, themes as JSON
files (light + dark palette in one file) in a `themes/` folder, built-ins
compiled into the core, a template emitter. The theme adds diff roles
(addition/deletion/context/tints/markers) on top of the syntax style
table.

## 4. Repository layout & build

```
prchum/
├── PLAN.md
├── Makefile                # single entry point: core / build / run / test / smoke / check / app
├── core/                   # Rust workspace
│   ├── prchum-core/        #   diff model, parser, locations, session, sources, export, config
│   ├── prchum-forge/       #   forge seam + gh/glab adapters (subprocess)
│   └── prchum-ffi/         #   C ABI surface (staticlib) + cbindgen config
└── macos/
    ├── Package.swift       # CPrchum (header shim) · PrchumKit (safe wrapper) · Prchum (app)
    ├── Info.plist
    └── Sources/
        ├── CPrchum/        #   empty shim.c + generated include/prchum.h (committed)
        ├── PrchumKit/      #   the only place pointers appear
        └── Prchum/         #   the app: windows, views, menus
```

Build flow is textchum's: `make core` (cargo builds `libprchum.a` +
regenerates the header via `build.rs`) → `make build` (`rm -f` the stale
binary — SwiftPM does not track the `.a` — then `swift build`).
`make smoke` runs the app with `--smoke-test`, a headless Swift↔core
round trip; `make header-check` diffs the committed header; `make check`
= tests + smoke + header-check (what CI runs). `make app` produces a
double-clickable `Prchum.app` in `dist/`. Testing: core logic in Rust
(parser round-trips, relocation tables, exchange byte-identity, submit
partitioning against a scripted fake `gh`), FFI exercised by the ffi
crate's own tests through raw pointers, the smoke test as the
integration layer.

## 5. Phases

Each phase ends with something usable.

### Phase 0 — Walking skeleton
- Repo scaffolding, Makefile, this plan committed.
- Core: diff model + unified parser; `pc_version()`; session over a patch
  file; row/file queries over the C ABI; event callback round trip.
- Swift: Package.swift three-target setup, PrchumKit wrappers, one window
  rendering a parsed diff read-only (file sidebar + unified rows with
  add/del coloring), `--smoke-test`.
- **Exit:** `make run -- some.diff` shows the diff natively;
  `make check` green from a clean checkout.

### Phase 1 — A real patch reviewer
- Cursor + keyboard grammar (j/k/J/K, hunks, files, counts, gg/G).
- Selection (v/V, one-side-one-range validation), draft comments with the
  inline editor, gutter markers, inline preview boxes, edit/delete/dismiss.
- Draft persistence per source key, atomic; Markdown export.
- Folding, search, unified↔split with semantic cursor re-anchoring.
- **Exit:** a patch file can be fully reviewed and exported; drafts
  reload across launches.

### Phase 2 — Sources & exchange
- Local git sources (worktree, staged, base, range) via the git binary.
- Exchange format: read/triage/writeback, byte-identical round trips —
  interop with leanreview verified against its own test vectors.
- Context view (whole file with hunks overlaid, verified against content,
  gap rows uncommentable), content cache.
- **Exit:** the LLM review loop works end-to-end in prchum on files
  leanreview produced, and vice versa.

### Phase 3 — Forges (the heart)
- Forge seam + `gh` adapter: PR metadata, canonical diff, threads (◆,
  thread reader, replies), general comments, attachments with signed-URL
  resolution.
- Submit sheet: atomic review, staged replies, retry-safe accounting;
  relocation when the head moves; orphan handling.
- `glab` adapter: reconstructed diff, positioned discussions, suggestion
  rewrite, approve/request mapping.
- Discovery list with named filters.
- **Exit:** a real GitHub PR reviewed and submitted from prchum;
  leanreview's acceptance semantics (nothing sent before confirmation,
  partial-failure retry never duplicates) hold.

### Phase 4 — Syntax & polish
- tree-sitter highlighting (three-tier fidelity), syntax modes, tints.
- Themes + appearance, Settings window, config escape hatches.
- Suggestions (```suggestion fences), PR info & general comments screens,
  images in comments.
- App icon, `make app` bundle, release workflow.
- **Exit:** daily-drivable; a v0.1 anyone can install from a zip.

### Phase 5 — Stretch
- `prchum://` scheme + `pr` CLI; keymap presets; a second shell (GTK)
  if ever wanted — the core is already portable.

## 6. Top risks & mitigations

| Risk | Mitigation |
|---|---|
| Inline comment boxes fight NSTableView row reuse | Flat custom view fallback is planned, not improvised; rows are core-provided models either way |
| Diff parser drifts from git/GitHub reality | Round-trip property tests on real git output; PR mode always uses the host's canonical diff |
| FFI churn slows iteration | textchum's proven conventions copied wholesale; grow the surface slowly |
| gh/glab output shapes change | Same seam leanreview uses in production; scripted fake `gh` for tests |
| Exchange-format drift breaks leanreview interop | Byte-identity tests against leanreview's own vectors |
| Scope creep toward a git client | §1 out-of-scope list; the core has no write path to the repo |
